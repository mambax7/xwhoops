<p><strong>xWhoops</strong> brings Whoops error display to XOOPS. An unhandled error becomes a screen naming the exception, with the stack frames that led there, the source for whichever frame you click, and the state of the request that triggered it. It takes the exception and shutdown handlers only -- notices and warnings still reach XoopsLogger and DebugBar -- and shows only to an authenticated administrator whose group holds the use_xwhoops permission. For developers and troubleshooting; not for a live site.</p>

<h5>2.0.0-Beta2 [2026-08-08]</h5>  Dev: XOOPS 2.7.3, PHP 8.5
<hr>
Adopts the error-screen provider seam introduced in XOOPS 2.7.3.
- Whoops is never handed the error handler at all. Its register() takes all three handlers (error, exception, shutdown - Run.php 216-218) and this module never returned one, although the README, install notes, both changelogs and its own status message have always said "the exception and shutdown handlers only". Every notice and warning was becoming an ErrorException and rendering a full Whoops screen, so a harmless E_WARNING during boot replaced the page. XoopsLogger and DebugBar now get what they always got; uncaught exceptions and fatals are unaffected. The mechanism is a Whoops\Util\SystemFacade subclass passed to Run::__construct() whose setErrorHandler() and restoreErrorHandler() do nothing; calling restore_error_handler() after register() instead would unbalance Whoops' own unregister(), which restores BOTH handlers on the way out (Run.php 231-241) and would then pop a frame this module had already taken back.
- Static analysis now sees the XOOPS APIs this module calls: stubs/xoops.stub gained XoopsModule::setMessage() and isactive(), XoopsModuleHandler, xoops_getHandler(), redirect_header(), Xmf\Request, and the three xoops_*ErrorScreenOwner functions XOOPS 2.7.3 publishes. Declaring the seam functions in the stub is not permission to drop the function_exists() guards around them - the module still runs unchanged on 2.7.2. Chosen over regenerating phpstan-baseline.neon, which would have been quicker: nearly all the errors sat in files this release adds or rewrites, so a fresh baseline would have frozen the new error-screen ownership API as permanently unanalysable.
- admin/index.php no longer assigns the result of ExampleClass::flawedMethod(), which returns void and in fact never returns at all - it throws, which is the point of the Example demo. Harmless, and wrong; found by PHPStan.
- The three module lifecycle hooks in include/errorscreen.php take \XoopsModule natively rather than an untyped $module. They previously carried a comment claiming the loose signature protected a recoverable branch; it did not - the next statement dereferences $module, core passes a real XoopsModule, and bundled core modules already type these hooks.
- Added tests/Unit/ErrorScreenContractTest.php: the provider obligations the 2.7.3 seam defines - refuse when developer_request is false or absent, ignore a token that is not ours, answer the legacy spelling, register nothing without a reporting channel, and keep the owner token equal to the dirname. The gate is advisory by core's design, so this module's refusal is the only thing between Whoops and an anonymous visitor. Its tearDown() pops the handler stack instead of pushing the original handler back on top: set_error_handler() adds a frame and restore_error_handler() removes one, so the tidier-looking version left the stack a frame deeper than PHPUnit saw and marked every case risky, which with failOnRisky turned the gate red.
- Registration is now the LAST thing registerWhoops() does. register() is the moment Whoops takes PHP's exception and shutdown handlers, and addDataTableCallback() used to run after it - so a throw while wiring the Queries panel left Whoops holding the handlers while this module reported 'error'. Since that failure is caught here, core's own catch never ran. Core hands the two handlers back on an 'error' report, but a shutdown function cannot be unregistered by anybody, so the rest is closed by having nothing fallible left to do.
- Registration moved from eventCoreIncludeCommonAuthSuccess to eventCoreDebugErrorscreen, so xWhoops takes PHP's handlers only when the site has declared it the owner. Whoever registers last owns them, so before the seam this module both displaced and was displaced by others, decided by module weight and id.
- The legacy entry point is kept and stands down when the seam is present, so one file works on 2.7.2 and 2.7.3 alike.
- Uses the core's shared developer check instead of isAdmin($mid), which answers "admin of whatever module we are inside". The module's own use_xwhoops permission is still checked separately.
- Claims the error screen at install, releases it at uninstall, takes it from an inactive holder at update. Deactivating does NOT release it.
- Reports its outcome in every branch, including the ones where it does not register. Previously Whoops could hold the handlers while the site's diagnostics said XoopsLogger did.
- On 2.7.3+ the error screen is activated by xoops_data/data/debug.php only; Admin -> Preferences -> Debug Mode no longer activates it. A site running Debug Mode alone sees the status "dormant" rather than silence.
